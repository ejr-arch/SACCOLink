SEGMENT 2 - THE PROBLEM BEING SOLVED                   0:35 - 1:35   (1:00)
--------------------------------------------------------------------------------
[CAMERA] Speak conversationally about the real-world context:

MAIN TALKING POINTS:
  * Background: SACCOs collect savings and give loans to their members.
    A member's repayment discipline and savings history are recorded inside
    one SACCO only.
  * Problem: when that member approaches another lender (for example a bank)
    for a bigger loan, the lender has NO quick, trustworthy way to see the
    member's actual credit track record. History stays locked inside the
    SACCO's books; verification is slow, paper-based and easy to fake.
  * Solution: SACCOLink stores each member's loans, savings and computed
    credit score, and issues a short-lived "credit passport" - a token with a
    72-hour expiry - that the member can hand to a bank. The bank enters the
    token, the system verifies it and returns the genuine score and band.
  * Users: SACCO staff (registration, loans, review), members (own history,
    loan requests, passports), and banks (verification).
  * Scope: eight tables, multi-user login, scoring, passport generation and
    verification; no mobile-money integration (kept out of scope deliberately).

SEGMENT 3 - DATABASE DESIGN (ERD + RELATIONAL)         1:35 - 3:15   (1:40)
--------------------------------------------------------------------------------
[SCREEN] Show the ERD image (docs / saccolink_erd.png, Figure 2.1 in report).
[CAMERA + SCREEN] Point at entities with the mouse as you speak:

MAIN TALKING POINTS:
  * Eight entities: MEMBER, LOAN_RECORD, SAVINGS_RECORD, CREDIT_SCORE,
    CREDIT_PASSPORT, CONSENT_AUDIT, APP_USER, LOAN_REQUEST.
  * Show the relationships and cardinalities:
      MEMBER 1---* LOAN_RECORD
      MEMBER 1---* SAVINGS_RECORD
      MEMBER 1---1 CREDIT_SCORE (current score)
      MEMBER 1---* CREDIT_PASSPORT
      MEMBER 1---* CONSENT_AUDIT (every consent change logged)
      APP_USER *---1 MEMBER   (a member login maps to one member)
      LOAN_REQUEST *---1 MEMBER
  * Logic of the design: everything hangs off the member; a passport is a
    snapshot of the score so a bank verifies a frozen, timestamped record.
  * Normalization: designed to at least Third Normal Form - no repeating
    groups, no partial dependencies (e.g. member details stored once in
    MEMBER, not repeated on every loan/savings row), no transitive
    dependencies (score band is DERIVED by a function, not stored redundantly).
  * Logical model: primary keys are NUMBER + sequences, foreign keys reference
    the parent keys, plus NOT NULL, unique (NIN) and check constraints.

SEGMENT 5 - SQL QUERY DEMONSTRATIONS                   5:45 - 7:45   (2:00)

[SCREEN] Run the queries one by one. These are the exact queries from
sql/07_queries.sql. For each, say in ONE sentence what it does and what it

TIP: paste each query instead of typing it; if time is tight, run these live
in this order: 1, 2, 3, 4a, 5a, 6.

QUERY 1 - SELECT with WHERE + ORDER BY:
   SELECT FULL_NAME, PHONE_NUMBER, DISTRICT
     FROM MEMBER
    WHERE DISTRICT = 'Kampala'
    ORDER BY FULL_NAME;
   >> 1 row: Grace Namukasa | 0772000001 | Kampala
   Say: "WHERE filters, ORDER BY sorts."

QUERY 2 - AGGREGATES + GROUP BY + HAVING (savers above 5,000,000 UGX):
   SELECT m.FULL_NAME,
          COUNT(s.SAVINGS_ID)              AS MONTHS_SAVED,
          NVL(SUM(s.AMOUNT_CONTRIBUTED),0) AS TOTAL_SAVED
     FROM MEMBER m
     JOIN SAVINGS_RECORD s ON s.MEMBER_ID = m.MEMBER_ID
    GROUP BY m.MEMBER_ID, m.FULL_NAME
   HAVING NVL(SUM(s.AMOUNT_CONTRIBUTED),0) > 5000000
    ORDER BY TOTAL_SAVED DESC;
   >> 4 members: Grace 24,000,000 · Betty 12,000,000 · Hassan 6,000,000 ·
      Sarah 5,400,000
   Say: "COUNT and SUM aggregate, GROUP BY builds the groups, HAVING filters
   the groups AFTER aggregation - that is why it is not WHERE."

QUERY 3 - THREE-TABLE JOIN (passport + member + score):
   SELECT p.QR_TOKEN, m.FULL_NAME, m.NIN, s.SCORE_VALUE, s.SCORE_BAND,
          p.PASSPORT_STATUS, p.EXPIRES_AT
     FROM CREDIT_PASSPORT p
     JOIN MEMBER m        ON m.MEMBER_ID = p.MEMBER_ID
     JOIN CREDIT_SCORE s  ON s.SCORE_ID  = p.SCORE_ID
    WHERE p.PASSPORT_STATUS = 'ACTIVE'
    ORDER BY p.EXPIRES_AT;
   >> 4 rows: Grace (810 EXCELLENT), Sarah (788.18 EXCELLENT), Betty (801.43
      EXCELLENT) and John (561 GOOD) - one ACTIVE passport each
   Say: "One query pulls the passport, the member it belongs to and the score
   it was based on - that is exactly why the data is normalised."

QUERY 4a - SCALAR SUBQUERY (savers above the organisation average):
   SELECT m.FULL_NAME, NVL(SUM(s.AMOUNT_CONTRIBUTED),0) AS TOTAL_SAVED
     FROM MEMBER m
     JOIN SAVINGS_RECORD s ON s.MEMBER_ID = m.MEMBER_ID
    GROUP BY m.MEMBER_ID, m.FULL_NAME
   HAVING NVL(SUM(s.AMOUNT_CONTRIBUTED),0) >
          (SELECT AVG(AMOUNT_CONTRIBUTED) FROM SAVINGS_RECORD)
    ORDER BY TOTAL_SAVED DESC;
   >> 6 rows (everyone except Amina - her 100,000 is below the ~232,719
      average)
   Say: "The inner SELECT returns ONE value that the outer query compares
   against."

QUERY 4b - IN SUBQUERY (members who have taken a loan):
   SELECT FULL_NAME, PHONE_NUMBER, DISTRICT
     FROM MEMBER
    WHERE MEMBER_ID IN (SELECT DISTINCT MEMBER_ID FROM LOAN_RECORD)
    ORDER BY FULL_NAME;
   >> 6 rows (everyone except Amina - she has no loan)

QUERY 4c - CORRELATED SUBQUERY (loans bigger than the member's own average):
   SELECT m.FULL_NAME, l.LOAN_AMOUNT, l.LOAN_STATUS
     FROM LOAN_RECORD l
     JOIN MEMBER m ON m.MEMBER_ID = l.MEMBER_ID
    WHERE l.LOAN_AMOUNT >
          (SELECT NVL(AVG(l2.LOAN_AMOUNT),0)
             FROM LOAN_RECORD l2
            WHERE l2.MEMBER_ID = l.MEMBER_ID)
    ORDER BY m.FULL_NAME;
   >> 6 rows on a fresh install - the loans bigger than their OWNER'S average:
      Grace 3,000,000, Betty 4,000,000, Hassan 2,000,000, John 2,000,000 and
      2,500,000, Sarah 1,500,000
   Say: "Here the inner query runs AGAIN for every outer row - it references
   the outer member."

QUERY 5a - UNION (deduplicated merge):
   SELECT MEMBER_ID, 'HAS_ACTIVE_PASSPORT' AS CATEGORY
     FROM CREDIT_PASSPORT WHERE PASSPORT_STATUS = 'ACTIVE'
   UNION
   SELECT MEMBER_ID, 'HAS_CURRENT_SCORE' AS CATEGORY
     FROM CREDIT_SCORE WHERE IS_CURRENT = 'Y'
    ORDER BY MEMBER_ID;
   >> 7 rows (every member, duplicates removed)

QUERY 5b - INTERSECT (rows in both):
   SELECT MEMBER_ID FROM LOAN_RECORD
   INTERSECT
   SELECT MEMBER_ID FROM SAVINGS_RECORD
    ORDER BY MEMBER_ID;
   >> 6 rows (members 1,2,3,5,6,7 - those with BOTH a loan and savings)

QUERY 5c - MINUS (rows in the first only):
   SELECT MEMBER_ID FROM CREDIT_SCORE WHERE IS_CURRENT = 'Y'
   MINUS
   SELECT MEMBER_ID FROM CREDIT_PASSPORT
    ORDER BY MEMBER_ID;
   >> 3 rows (members 2, 3, 4 - Okello, Hassan and Amina: scored but never
      generated a passport)

QUERY 6 - VIEW (reporting through V_PASSPORT_DETAIL):
   SELECT FULL_NAME, SCORE_BAND, PASSPORT_STATUS
     FROM V_PASSPORT_DETAIL
    WHERE SCORE_BAND = 'EXCELLENT';
   >> 3 rows (Grace, Sarah and Betty - the three EXCELLENT passports; John's
      561 is GOOD)
   Say: "Reports select from a VIEW, so the join is written once and hidden
   from the query."
